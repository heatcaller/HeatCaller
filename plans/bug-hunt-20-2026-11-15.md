### 1. At a club that doesn't do tech inspection, nobody on Who's Racing ever shows as "Ready to race". Every driver is stuck on "Tech: car not looked at yet" with an Inspect Car button.

`HeatCaller/HeatCaller/CheckInControl.Board.cs:69` · medium · confirmed

**What happens.** The club has no tech checklist on any class and has logged no inspections tonight, so no class runs tech. A driver checks in and pays. Desk mode shows 'Tech: car not looked at yet' with Inspect Car..., the Ready column reads 2/3 instead of Ready, the strip shows 'Through tech 0 of N here' and 'Ready to race 0 drivers', and the Needs tech chip counts everyone. The file's own header says the tech gate applies only 'when the club runs it'.

**Code path.** CheckInControl.Board.cs:69-76 sets Tech = Gate.NotRun only when _tech is null. MainForm.Pages.cs:560 always passes _techInspections (MainForm.cs:292, never null). For a club with no tech, JudgesTechFor (CheckInControl.cs:1078 -> RaceControlControl.NextUp.cs:101-106, TechIsRunFor false for every class) is false. TechInspectionStore.LatestForDriver:270-272 then falls back to Latest(main class), which is null, so the gate is Gate.Open. Readiness.Ready (Board.cs:28) needs every gate that runs to be Done, so Ready is never true. The desk card (Desk.cs:363-366) and RefreshCounts (Board.cs:263, 293-300, 318-319) show the same.

**Verifier.** MainForm.Pages.cs:560 always passes _techInspections, so _tech is never null and the Tech gate is never NotRun. When no class runs tech, LatestForDriver (TechInspectionStore.cs:270-272) falls back to Latest(main class), which is null, so the gate is Open. Readiness.Ready then needs Tech == Done and is never true. The desk card shows 'Tech: car not looked at yet' (Desk.cs:358-359), and the Needs tech chip and Through tech tile appear because they check _tech != null. No test covers Readiness.

### 2. A driver who paid for one class and is then put in a second class at the desk still shows as paid and ready. Nothing says they owe the extra class fee.

`HeatCaller/HeatCaller/CheckInControl.Board.cs:80` · medium · confirmed

**What happens.** Day fee is $15 and the extra-class fee is $10. Sam pays $15 cash at the desk. Then he says 'I'm running Mod too', and the volunteer ticks Mod in his Class cell. His fee is now $25, but the Paid cell still reads 'Cash $15.00'. The gate counts as Done, the desk card says 'Paid: Cash $15.00 · ready to race', he drops out of the Owes chip and the strip's '$N owed', and the closing checklist's money line treats him as settled. The $10 is never collected.

**Code path.** CheckInControl.Classes.cs:127-160 ChangeClass changes the driver's classes, and FeeFor (Money.cs:35-47) then returns the higher fee. ReadinessOf (Board.cs:78-84) counts the driver as settled whenever payment.How != Owing, whatever payment.Amount is against FeeFor. DeskMoney.Words (DeskMoney.cs:240-246) shows only the amount stored by Settle (Money.cs:130). MainForm.NightClose.cs:77 checks How == Owing only.

**Verifier.** ReadinessOf (Board.cs:83) treats any How != Owing as settled, whatever is in payment.Amount. Settle stores the amount at the moment it is pressed (Money.cs Amount = FeeFor). ChangeClass changes the classes without touching the payment. DeskMoney.Words shows the stored amount, and NightClose checks How == Owing only. Nothing compares Amount with the new FeeFor, so the extra-class fee goes uncollected without anyone being told. The bug hunt 19 signature fix in Desk.cs:261-263 only redraws the card.

### 3. After a race, the championship update can name the wrong class: once the next round is picked, the AI says the last race's points table belongs to the next round's class ("Dot takes over the lead of the Stock championship" about the Mod table).

`HeatCaller/HeatCaller/CommentaryDirector.cs:1011` · medium · confirmed

**What happens.** A Mod heat finishes and is filed. The race director then picks the Stock A-main in the Round box (by hand, or from Next Up) and leaves it there for a while before the green. On the next announcer tick, AnnouncerControl.Director.cs:1974 calls ClassBetweenRaces(_activeRound?.ClassName), so _className becomes "Stock". The Championship check segment still gets its table from the LAST FILED race: MainForm.Commentary.cs:1111 builds it with ChampionshipAfter(LastFiledResults(), filedRound, ...), which is the Mod championship. Candidates(ChampionshipCheck) (CommentaryDirector.cs:3050-3053) passes that Mod table with className = "Stock" into CommentaryReportFacts.ChampionshipCheck, which puts the class into every sentence: "{leader} leads the {cls} championship", "takes over the lead of the {cls} championship from ...", "level at the top of the {cls} championship" (CommentaryReportFacts.cs:373-406). The PA then reads out Mod drivers' points as the Stock championship. The segment is also booked against Stock's per-class allowance (Budget.Reserve(kind, _className)). Before the bug hunt 17 change, _className stayed the last race's class and matched this table. That change fixed the qualifying report, which reads the picked round, but broke this segment, which reads the filed race.

**Code path.** AnnouncerControl.Director.cs:1974 ClassBetweenRaces(RaceClassName) -> CommentaryDirector.cs:1011-1019 sets _className to the picked round's class -> CommentaryDirector.cs:2249 CandidatesForPass(kind, _className) -> :3050-3053 ChampionshipCheck(table, className) where table = MainForm.Commentary.cs:1111 ChampionshipAfter(LastFiledResults(), filedRound) -> CommentaryReportFacts.cs:353/373-406 "... the {cls} championship"

**Verifier.** I traced the whole path. Between races, ClassBetweenRaces (CommentaryDirector.cs:1010-1019) sets _className to the round picked in the Round box (AnnouncerControl.Director.cs:1974). The Championship reader (MainForm.Commentary.cs:1097-1123) always builds its table from LastFiled() and the filed race's own round. Candidates(ChampionshipCheck) (:3050-3053) passes that table together with _className, and CommentaryReportFacts.ChampionshipCheck writes the class into every sentence. The tests only call ChampionshipCheck with a fixed class string, so none cover this mismatch. It fires only if the check has not already been spoken for that race key (the champlead:{raceKey} dedupe) when the next round is picked, but picking the next round before that happens is a normal workflow.

### 4. Renaming a class makes its old handicap races get scored on today's credits again, so an old meeting's handicap winner can change

`HeatCaller/HeatCaller/HandicapStore.cs:614` · medium · confirmed

**What happens.** Night 1: Stock runs on time credits, and the race is filed with its credits kept (Handicap.ClassName = "Stock"). Later the club renames Stock to "Stock 2WD". The rename cascade renames the rounds and the handicap class modes, but not SessionRecord.Handicap.ClassName. Race History (HandicapClassFor gives the round's new name "Stock 2WD") and the Event Report (grouped by round.ClassName) now call ForSession with "Stock 2WD". The kept snapshot's "Stock" doesn't match, so it falls back to the live HandicapStore. After the next Suggest Handicaps changes the credits, the old race is re-ranked and its handicap winner can change. That is the bug B52 was meant to stop, and it comes back after any rename. The same fallback hits the guest class of a shared (mixed-class) heat: Snapshot stores round.ClassName (the host class), and EventReportBuilder calls ForSession for each class in the heat, so the guest class's table is always scored on live credits.

**Code path.** RaceFilingService.cs:460 stores Snapshot(results, ..., round.ClassName) -> HandicapStore.cs:614 ForSession needs kept.ClassName == className, else uses live?.ModeFor + Apply(live) -> RaceHistoryControl.cs:1155 HandicapClassFor = round.ClassName (renamed by ClassRenameCascade via _rounds, MainForm.cs:988) and EventReportBuilder.cs:518-529/565 (className = round.ClassName or each MixedHeats.ClassesOf). Nothing renames SessionRecord.Handicap.ClassName (grep finds no writer except the Snapshot).

**Verifier.** The only thing that writes SessionHandicap.ClassName is Snapshot (RaceFilingService.cs:460, round.ClassName). The rename handler (ClassRenameCascade plus the MainForm.cs:990-1048 Renamed handler) renames rounds and _handicaps.RenameClass, and it rewrites MixedHeats stamps in saved sessions, but it never touches session.Handicap.ClassName. After a rename, HandicapClassFor (RaceHistoryControl.cs:1155) and EventReportBuilder.cs:565 pass the new name, the case-insensitive check at HandicapStore.cs:612 fails, and the code falls back to live ModeFor/Apply. That re-ranks the race on today's credits, which is exactly what B52 was meant to stop. The mixed-heat guest class has the same problem: the snapshot is keyed to the host class, but EventReportBuilder calls ForSession once for each class in MixedHeats.ClassesOf. The doc comment says the live fallback is meant for a race 'since linked to a round of another class', not for a rename or a shared heat. It needs a rename plus a later change to the credits, so it is medium.

### 5. A junior racing on one of the club's rental transponders is not recognised as a junior, so their race video can show on the public results.

`HeatCaller/HeatCaller/MainForm.Video.cs:90` · medium · confirmed

**What happens.** Juniors' races are kept off public race video because the relay is sent a list of races 'with a junior in them'. JuniorRacesToday builds that list by looking up each result's transponder and checking that profile's IsJunior flag. A junior trying the club out on rental R4 races under R4's transponder. That transponder's profile is the shared rental profile (IsRental = true), and the rental store keeps the renter only as a typed name (CurrentHolderName), never as a profile. So the lookup finds the rental profile, IsJunior is false, and the race is left off the list. The relay then shows that heat's YouTube moment on the public results with the child in it, against the club's rule that juniors stay on their own night.

**Code path.** MainForm.Video.cs:82-95 JuniorRacesToday -> _profiles.GetForAnyThread(r.Transponder) is { IsJunior: true }; the rental transponder resolves to the IsRental profile (MainForm.UnknownTransponders.cs:276-282 creates it with IsRental = true); RentalTransponderStore.CheckOut (RentalTransponderStore.cs:194-205) keeps only holderName, with no profile link -> StreamDocument (MainForm.Video.cs:37-42) sends the incomplete junior list to the relay

**Verifier.** Traced. JuniorRacesToday (MainForm.Video.cs:82-95) finds juniors only through the IsJunior flag on the profile of each result's transponder. By design a rental is lent by name only. RelaySignupDesk.Approve (around line 331) says 'Lent by name only, as at the counter - no profile for them on the club's unit', and RentalTransponderStore.CheckOut stores only holderName.
