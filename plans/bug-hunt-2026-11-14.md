### 4. Opening a driver from Who's Racing (double-click) or the leaderboard's Edit Driver and saving puts back a car the driver picked on their phone while the dialog was open, so they get announced and tagged in the old car.

- **Where:** `HeatCaller/HeatCaller/DriverEditDialog.cs:69`
- **Severity:** medium, confirmed
- **Fix:** fixed, `6f154fe`

**When it fires.** At check-in the desk double-clicks Sam on Who's Racing and the Edit Driver Profile dialog opens. While it is open, Sam picks a different car for tonight on his phone. The roster tick runs FileWaitingWrites -> ApplyCar -> _profiles.Upsert(after) with the new CarModel. The desk changes something else (or nothing that touches the car) and clicks Save. DriverEditDialog then calls profiles.Upsert(form.Result). That Result was built from the dialog's boxes, which still show the old car, so Sam's phone pick is gone. His phone was already told the change was approved.

**Code path.** DriverEditDialog.cs:24-69 builds a ProfileForm on the live profile and then calls `profiles.Upsert(saved)` directly. ProfileForm.cs:1197 sets Result to a brand-new profile built from the boxes and from the profile it was opened on. The phone path, DriverRequests.Garage.cs:603-631, calls `_profiles.Upsert(after)` on the roster tick, and that tick keeps running while a modal dialog is open. Driver Hub's own edit path guards this case: ProfileManagerControl.cs:2307 calls `_store.Upsert(ProfileStore.KeepChangesMadeSince(before, form.Result, _store.Get(transponder)))`, added in bug hunt 15 for exactly this phone-pick race. The new shared DriverEditDialog (13 Nov), now behind the Who's Racing double-click as well as the leaderboard, does not have that guard.

**Verifier check.** I traced the failure through the code. DriverEditDialog.Edit (HeatCaller/HeatCaller/DriverEditDialog.cs:16-22) opens ProfileForm on the profile as it is on file when the dialog opens. On Save, ProfileForm.BtnSave_Click (ProfileForm.cs:1186-1197) sets Result = ProfileAsShown(). ProfileAsShown builds a brand-new DriverProfile, with CarModel taken from _cmbCars.Text and Cars from the combo items (ProfileForm.cs:1215-1227), so both still hold the car shown when the dialog opened. DriverEditDialog then calls profiles.Upsert(saved) directly at line 73 (the claim says 69). Nothing merges in changes made on file since the dialog opened.

The phone path runs while the dialog is open:
- _webRosterTimer is a WinForms timer whose Tick calls RosterTickDriverRequests (MainForm.cs:1380-1409). A WinForms timer keeps firing inside a modal ShowDialog loop, and RosterTickDriverRequests has no modal guard; it only checks _closingDown (MainForm.DriverRequests.cs:140).
- That tick calls FileWaitingWrites (DriverRequests.Garage.cs:51). For a Car request, ApplyCar handles the "tonight" case by calling RaceTonight (line 472-479), which needs no desk step (NeedsDesk covers only marshal-cover swaps).
- RaceTonight saves the new active car with _profiles.Upsert(after) (line 631) and tells the phone "You're racing X".

So the dialog's save puts the old CarModel back over the phone's pick.

Driver Hub's edit path guards this exact race: ProfileManagerControl.cs:2307 saves through ProfileStore.KeepChangesMadeSince (ProfileStore.cs:933-982, whose comment describes this phone-pick bug from bug hunt 15, with tests in BugHunt15_EditProfileKeepsPhoneChangesTests). DriverEditDialog does not use that guard. Its two callers are the Who's Racing double-click (CheckInControl.cs:1307) and the leaderboard's Edit Driver (RaceControlControl.Leaderboard.cs:1796).

The undo DriverEditDialog sets up only checks the record at undo time; it does not prevent the overwrite. plans/bug-hunt-2026-11-13.md does not mention DriverEditDialog or KeepChangesMadeSince, so this has not been reported before.

Severity is medium. It needs a phone car pick to land in the seconds-to-minutes window while the desk has this dialog open. When it does, the phone is told the change worked but the old car stays on file, so the driver is announced and tagged in the wrong car. No results or points are lost, and the driver can pick the car again.

**Suggested fix.** Take `var beforeSnap = existing is null ? null : ProfileStore.Snapshot(existing)` before the form opens. On save, store `beforeSnap is null ? saved : ProfileStore.KeepChangesMadeSince(beforeSnap, saved, profiles.Get(transponder))`, and compute `after` from that merged profile so the undo guard still matches.

**What was done.** Confirmed: when the dialog was saved, DriverEditDialog.Edit wrote form.Result straight back with Upsert. It now takes a ProfileStore.Snapshot when the dialog opens, and saving goes through a new DriverEditDialog.ToSave, which calls ProfileStore.KeepChangesMadeSince(openedOn, edited, profiles.Get(transponder)). The undo's 'after' guard is now worked out from the merged profile, so undo still matches what was saved. A new driver (nothing on file when the dialog opened) is still saved exactly as typed.

**Tests.** Added HeatCaller/HeatCaller.Tests/BugHunt18_DialogsKeepPhoneCarPickTests.cs with 3 tests: Edit Driver keeps a phone car pick, a new driver is saved as typed, and Import Entries keeps a phone car pick while still adding its class. They call the new helpers, so they will not compile without the fix. Ran: dotnet test HeatCaller/HeatCaller.Tests/HeatCaller.Tests.csproj --artifacts-path HeatCaller/HeatCaller.Tests/bin/claude-run --filter "FullyQualifiedName~BugHunt18_DialogsKeepPhoneCarPickTests|FullyQualifiedName~EntryImportTests|FullyQualifiedName~BugHunt15_EditProfileKeepsPhoneChangesTests". Result: 41 passed, 0 failed. The modal dialog wiring itself (ShowDialog plus the roster tick) is UI-only and was not tested end to end.

### 8. In a qualifier run on 'own clock from 1st crossing', or a staggered start on 'Clock: own release', a backmarker's phone says "Leader behind" at the wrong moment (too early, or never) because the leader's and the backmarker's race times are compared as if they ran on one shared clock.

- **Where:** `HeatCaller/HeatCaller/LeaderBehind.cs:75`
- **Severity:** medium, confirmed
- **Fix:** fixed, `2a51898`

**When it fires.** Run a qualifier with the Qualifying start type (set by the IFMAR/BRCA presets), or a staggered start with StaggerClock.OwnRelease, with the relay's lap voice on. The leader comes up to lap a backmarker whose clock zero (first crossing, or release offset) is a few seconds away from the leader's. For example, the backmarker first crossed 3 s after the leader, and the leader is really 5 s behind it on track. On the per-car clocks the leader looks about 2 s behind, so 'Leader behind' is said most of a lap early. The phone keys on the approach number, so it then stays silent when the leader really arrives. The opposite offset pushes the leader's crossing to 'at or before ours', and no warning is given at all.

**Code path.** LeaderBehind.Approach(car, leader) (LeaderBehind.cs:70-79) passes car.ElapsedMs - PenaltyMs and leader.ElapsedMs - PenaltyMs straight into the history overload. That overload (lines 91-150) finds the leader's crossing at or before carElapsedMs and computes behind = next - carElapsedMs, treating both as one race clock. In the live session, though, ElapsedMs is per-car: RaceControlSession.Laps.cs:361-384 sets elapsedSinceStart = sinceGreen - standing.QualifyingZeroMs for a Qualifier start, and lines 386-396 subtract standing.ReleaseOffsetMs under StaggerClock.OwnRelease. The only caller, WebServerService.cs:2933, calls it for every race whatever the start type. The penalty fix from bug hunt 17 (#14) corrected the penalty skew only, not the clock zero. The same mistake in RaceLines is #24 in the 13 Nov report. This feature and file are separate from that one.

**Verifier check.** I traced it through the code and it holds. RaceControlSession.Laps.cs:361-384 (in HeatCaller.Timing, not HeatCaller) sets elapsedSinceStart = sinceGreen - standing.QualifyingZeroMs for a Qualifier start. Lines 386-395 subtract standing.ReleaseOffsetMs under StaggerClock.OwnRelease. Line 757 stores standing.ElapsedMs = elapsedSinceStart + PenaltyMs, so ElapsedMs runs on each car's own clock. LeaderBehind.Approach(car, leader) at LeaderBehind.cs:74-79 takes off only PenaltyMs. It never adds back QualifyingZeroMs or ReleaseOffsetMs. It passes both times to the history overload, which compares them as one track clock: line 119 looks for the leader's crossing with t <= carElapsedMs, and line 137 sets behind = next - carElapsedMs. If the two clock zeros differ by D, 'behind' is off by D. That gives an early false warning, or none, the same way the penalty skew did in #14. The only caller is WebServerService.cs:2933, and it runs for every race without checking the start type. There is no guard and no comment calling this intended. LeaderBehindTests has no qualifying-start or release-offset case. The 13 Nov report lists #14 (penalty skew in LeaderBehind) and #101 (ghost leader), both already fixed in this code. It also lists #24, the same per-car-clock mistake but in RaceLines.cs. None of these is the LeaderBehind clock-zero bug, so it is not already reported. Severity is medium: it is a voice cue, not a scoring error. But qualifiers on the IFMAR/BRCA presets and OwnRelease staggers are common setups, and offsets of a few seconds are normal. The phone says the warning once per approach number, so a false early call also uses up the real one.

**Suggested fix.** Put each car's times back on the since-green clock before comparing them: add QualifyingZeroMs (Qualifier start) or ReleaseOffsetMs (own-release stagger), which RacerStanding already carries. Or have WebServerService skip 'lapping' when the race is not on one shared clock.

**What was done.** LeaderBehind.Approach(car, leader/ordered) now takes startType and staggerClock (defaults Standard/SharedGreen) and adds each car's clock zero back via the existing RaceControlControl.ClockZeroSinceGreenMs (qualifier first crossing, OwnRelease release offset, never for ghosts) after taking the penalty off, so both cars are compared on the since-green clock. WebServerService passes _race.StartType and _race.StaggerClockMode when building the relay's 'lapping' field.

**Tests.** Added HeatCaller/HeatCaller.Tests/BugHunt18_LeaderBehindClockTests.cs (qualifier with 0.5 s first-crossing offset: call was lost, now given; OwnRelease leader released 1.5 s late: false early call, now none; SharedGreen ignores release offset). Both fail without the fix (behind read 3.0 s -> null, and 2.0 s -> call). Ran dotnet test ... --filter "FullyQualifiedName~LeaderBehind": 17 passed, 0 failed (includes LeaderBehindTests and BugHunt17_LeaderBehindTests).

### 12. After a driver sorts the Personal Bests table by a column header, each track's pill (Solid / In reach / One-off / Fresh) and its 'races near it' dots belong to a different track, because the readings are stored by row index from before the sort.

- **Where:** `HeatCaller/HeatCaller/PersonalBestsControl.cs:437`
- **Severity:** medium, confirmed
- **Fix:** fixed, `d967dea`

**When it fires.** Open Personal Bests for a driver with PBs on two or more tracks (for example Track A is Solid, Track B is a One-off). Click the 'Track' or 'PB' column header so the rows reorder. Track A's row now shows Track B's red 'One-off' pill and B's dots, while the 'What it means' text in the same row still describes Track A. A row waiting after a reset (it has no entry in _reads) can also take another row's pill, or a real row can lose its pill.

**Code path.** RefreshGrid stores each reading by the index of the row when it was added: `_reads[row] = read;` (PersonalBestsControl.cs:437, where row = _grid.Rows.Add(...)). PaintReading looks it up by the index the row is painted at: `_reads.TryGetValue(e.RowIndex, out var read)` (line 489), sets e.Handled = true and paints over the cell text. The columns (lines 145-152) are plain DataGridViewTextBoxColumns, which sort automatically when a header is clicked, and SortMode is never set to NotSortable here. The new verdicts grid in PaceAnalysisControl does set NotSortable (line 648), which shows the risk is known. Sorting moves the rows but leaves _reads keyed by the old indices.

**Verifier check.** Confirmed. I traced it through the code. In PersonalBestsControl.cs:33 `_grid` is a plain `DataGridView` with no data source. The columns at lines 144-153 are `DataGridViewTextBoxColumn`s, and none of them sets `SortMode`, so each one keeps the default `Automatic`. Clicking a header therefore sorts the rows in place, and each row's `Index` changes. I searched the project for any shared helper or subclass that turns sorting off. There is none: every `NotSortable` in the project is set per column in other files (CarriedPointsForm, DriverPaidForm, PaceAnalysisControl:648, RaceHistoryControl:226 and others), and `Pieces.KeepHeadingsWhole` does not touch `SortMode`. RefreshGrid saves each reading under the row's index at the moment it was added: `var row = _grid.Rows.Add(...)` at line 428, then `_reads[row] = read;` at line 437. Rows waiting after a reset (lines 415-421) get no entry in `_reads`. PaintReading looks the reading up by the index the row is painted at, `_reads.TryGetValue(e.RowIndex, out var read)` at line 489, then paints the background over the cell and draws the pill or dots from `read` (lines 501-510+). That covers the 'real' and 'near' columns. Nothing clears or rebuilds `_reads` after a sort, because no Sorted or ColumnHeaderMouseClick handler exists. It is only rebuilt when RefreshGrid runs again. So after a sort, row N shows the pill and dots of whatever track was first added at index N. The text in Track, PB, Gap and What it means still describes the real track. A waiting row can pick up another track's pill, and a real row can lose its pill. No test or comment says this is intended. The comment at line 389 calls `_reads` 'What each row's reading is, by row'. It is not in plans/bug-hunt-2026-11-13.md: the only nearby match is a slice listing for PaceAnalysisControl, and nothing about PersonalBests sorting. Severity is medium. It is display only, with no data loss, and the reset buttons read the row's real cells through SelectedRow. But a header click is a common action, and the result tells a driver a wrong and contradictory PB verdict.

**Suggested fix.** Store the PbRead in each row's Tag and read it in PaintReading from _grid.Rows[e.RowIndex].Tag, or set SortMode = NotSortable on the PB grid's columns.

**What was done.** Confirmed: _reads was a Dictionary keyed by the row index at add time, and the columns sort automatically, so a header-click sort put the wrong pill and dots on each row. Replaced the dictionary with the row's Tag; a new internal ReadingAt(rowIndex) reads it back, and PaintReading uses it. Sorting stays enabled. Rows waiting after a reset have no Tag, so they get no pill.

**Tests.** Added RaceAnalyticsPersonalBestsTests.Sorting_by_a_heading_keeps_each_pill_on_its_own_track. It sorts the grid by Track descending, which reverses the Solid and One-off rows, then checks that each row's painted reading label matches its own "real" cell. With the old index-keyed lookup the two would be swapped. I did not run it against the old code to watch it fail. ### 14. The Next Up bar, the Big Screen band ("NEXT RACE IN 1:42") and the drivers' phone countdown add the warm-up, staging and countdown of the race that just finished, not the next race. When the two races run different formats, the time shown to the green is wrong by those steps.

- **Where:** `HeatCaller/HeatCaller/RaceControlControl.AutoStart.cs:570`
- **Severity:** medium, confirmed
- **Fix:** fixed, `4bd8ca8`

**When it fires.** Auto start is counting between races. The race just run (say a Stock heat, format with no warm-up and no auto-advance) is still in the Round box. The next race is another class, or a main instead of a qualifier, whose format has a 3-minute warm-up and auto-advance. The gap counts down 2:00, and the phones and Big Screen say "in 2:00". The race actually goes green about 2:00 + 3:00 + staging + countdown later. The opposite case happens too: a just-run race with a long warm-up makes the screens promise a late green for a next race that has none.

**Code path.** ToTheGreen (RaceControlControl.AutoStart.cs:558) adds StartToGreen(), and UpdatePhoneCountdown (RaceControlControl.Marshals.cs:472) does the same. StartToGreen (AutoStart.cs:562-573) reads EffectiveFormat(out _) (NextUp.cs:206). That method resolves its format from ShowRound() = _activeRound ?? DemoRound (Intros.cs:89). During the gap _activeRound is still the race just filed: the Round box only moves to the next round when Start Next / NextRoundStartRequested calls ApplyRoundToSessionSetup (MainForm.RaceSetup.cs:264/632). NextRound() (NextUp.cs:318) skips the active round on purpose, because that round is the one just run. So the gap's 'next' race is NextRound(), but the format used for its lead-in belongs to the previous race. The real start then runs TryBeginWarmUp/Stage/Countdown with the next round's format, after ApplyRoundToSessionSetup and ApplyEffectiveFormat.

**Verifier check.** I traced this through the code and the claim holds. During the gap, AutoStartTick (RaceControlControl.AutoStart.cs:369-392) opens the clock for `next = NextRound()`. NextRound (NextUp.cs:318-326) skips `_activeRound` on purpose, and line 381 names `_activeRound` as `lastRound`, the race just run (it feeds RecentlyRan and NightBreaks.Between). The Round box only moves when StartNext / StartRoundNow calls ApplyRoundToSessionSetup (MainForm.RaceSetup.cs:264, 632), so during the gap `_activeRound` is still the race that just finished.

ToTheGreen (AutoStart.cs:558-559) and UpdatePhoneCountdown (Marshals.cs:472) both add StartToGreen(). StartToGreen (AutoStart.cs:562-573) calls EffectiveFormat(out _) with no round argument. EffectiveFormat (NextUp.cs:206-235) resolves the format from ShowRound() = `_activeRound ?? DemoRound` (Intros.cs:89). That gives the just-run round's override, qualifier format or class format, not the format of the round being counted down. Only practice mode returns zero (line 564).

The behaviour is not intended. StartToGreen's own summary (line 561) says "How long the next race's start runs before its green, by its format". The tests (WarmUpFlagTests.cs:236-256) only pin the source strings and the pure LeadToTheGreen sums, never which round the format comes from. The real start resolves the next round's format only after ApplyRoundToSessionSetup has run.

The trigger is ordinary.
